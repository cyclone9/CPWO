الإصدار ‎1.0.0 (2026-10-24). انظر [CHANGELOG.md](CHANGELOG.md).

ملف تنفيذي واحد يصغّر ملفات HTML وCSS وJS، ويضغط الصور، ويحوّلها إلى WebP وAVIF.

لا يستخدم cgo، ولا يحتاج إلى تثبيت أي شيء على الجهاز الذي يشغّله.

<p align="center" dir="rtl">نظرة في 24 ثانية على CPWO. انقر على الصورة لفتح الفيديو، وهو بالإنجليزية.</p>

```
cpwo [flags] <project-path>...
```

وجِّهه إلى مجلد المشروع. يفحصه بما فيه من مجلدات فرعية ويكتب كل ناتج بجوار الملف الذي صدر عنه. ولا يعدّل CPWO أيًّا من ملفاتك المصدرية أبدًا. ويجوز وضع الخيارات قبل المسارات أو بعدها، فيعمل الأمر `cpwo ./site -avif`. وبعد العلامة `--` وحدها يُعدّ كل ما يليها مسارًا.

```
style.css   ->  style.min.css        photo.jpg  ->  photo.webp
app.js      ->  app.min.js           photo.jpg  ->  photo-512.webp   (with -r)
index.html  ->  index.min.html       logo.png   ->  logo.avif        (with -avif)
```

يكتب كل تشغيل أيضًا ملف ‎`.cpwo-output` في جذر المشروع، يسرد ما أنشأه. ويقرؤه التشغيل التالي ليفرّق بين ملفات CPWO وملفاتك.

## الخيارات

| الخيار | الافتراضي | ما يفعله |
|---|---|---|
| `-q <1-100>` | `82` | جودة JPEG وWebP المضغوط مع فقد. وتُشتق منها جودة AVIF بتحويل المقياس |
| `-r` | معطّل | يكتب أيضًا نسخًا بأحجام أخرى، بكل صيغة مفعّلة |
| `-sizes <list>` | `1024,512,256` | قيم العرض التي يستخدمها ‎`-r`. وضبطه يفعّل ‎`-r` |
| `-resize-fallback` | معطّل | يكتب نسخ JPEG/PNG بالأحجام الجديدة إلى جانب النسخ الأخرى. ويفعّل ‎`-r` |
| `-relink` | معطّل | يوجّه ‎`<link href>`‎ و‎`<script src>`‎ إلى ملفات ‎`.min.`‎ الموجودة. ولا يلزم أن يكون محدّثًا إلا ما أنتجه CPWO نفسه |
| `-picture` | معطّل | يغلّف ‎`<img>`‎ بعنصر ‎`<picture>`‎ فيه عنصرا ‎`<source>`‎ لصيغتي AVIF وWebP. ويترك ‎`<img>`‎ وشأنه إذا كانت له سمة `srcset` أو سمة `data-`‎ تحمل مسار صورة |
| `-exif` | معطّل | يُبقي بيانات EXIF من الملف المصدر في ‎`.min.jpg` المعاد ترميزه |
| `-only` | معطّل | لا يشغّل إلا المجموعات المذكورة في سطر الأوامر |
| `-overwrite` | معطّل | يعيد إنتاج الملفات التي أنتجها CPWO نفسه حتى لو كانت محدّثة. ولا يكتب فوق ملف لم ينتجه CPWO أبدًا |
| `-adopt` | معطّل | يتبنّى الملفات الموجودة أصلًا في المواضع التي يكتب فيها CPWO، كأن ‎`.cpwo-output` يسردها. ويفيد حين يضيع السجل أو لا يُودَع قط. وتُتبنّى كذلك ملفات المكتبات الخارجية الموجودة هناك، فراجع ‎`-v` أولًا |
| `-j <n>` | عدد أنوية المعالج | عدد المهام، أي عدد الملفات التي تُعالَج في وقت واحد |
| `-v` | معطّل | يطبع كذلك سطرًا لكل ملف، مع سبب ترك أي ملف على حاله. ويظل الملخص يُطبع |
| `-version` | | يطبع رقم الإصدار |
| `-license` | | يطبع رخصة CPWO (MIT) مع سطر حقوق النشر، ثم سطرًا لكل مكوّن مضمّن فيه (اسمه ورخصته والغرض من استخدامه). والنصوص الكاملة في [licenses.md](licenses.md) |
| `-help`, `-h` | | يطبع طريقة الاستخدام |

### رمز الخروج

| الرمز | المعنى |
|---|---|
| `0` | اكتمل العمل |
| `1` | تعذّرت معالجة بعض الملفات. يبلّغ CPWO عن كل ملف منها، ويستمر في بقية التشغيل بما فيه كتابة السجل |
| `2` | استخدام خاطئ، أو مسار غير موجود. ويتحقق CPWO من كل مسار قبل أن يبدأ أي عمل |

### اختيار ما يُشغَّل

المجموعات ‎`-html -css -js -json -svg -xml -img -webp` مفعّلة كلها افتراضيًا. فإذا ذكرت أيًّا منها لم يعمل إلا ما ذكرته.

يشذّ ‎`-avif` عن هذه القاعدة: فهو معطّل إلى أن تطلبه، ولذا فذكره *يضيف* إلى التشغيل المعتاد ولا يحصر التشغيل فيه وحده. ولا يمكن أن يكون الأمر بخلاف ذلك: فذكره هو السبيل الوحيد إلى تفعيله أصلًا، ولو كان يحصر التشغيل كما يفعل ‎`-webp` لما وُجدت طريقة لقول «المعتاد مع AVIF» إلا بذكر المجموعات التسع كلها صراحةً.

أما ‎`-only` فهو الوسيلة إلى تشغيله وحده، وهو يعمل مع أي مجموعة.

```sh
cpwo -webp ./site           # only WebP conversion
cpwo -avif ./site           # the usual run, with AVIF as well
cpwo -avif -only ./site     # AVIF and nothing else
cpwo -webp -avif ./site     # only the two image formats
cpwo -avif -js=false ./site # the usual run, plus AVIF, minus JS
cpwo -css -js ./site        # only CSS and JS
cpwo -js=false ./site       # everything except JS
```

يُعدّ استخدام ‎`-only` دون ذكر أي مجموعة خطأً، وليس تشغيلًا لا يفعل شيئًا.

يعيد ‎`-img` ضغط صور JPEG وPNG بالجودة ‎`-q`. ويكتب ‎`-webp` نظائر ‎`.webp`، ويكتب ‎`-avif` نظائر ‎`.avif`.

### صيغة AVIF

يكون AVIF عادةً أصغر بنسبة 30-50% من WebP للصورة نفسها، وتدعمه كل المتصفحات الحالية. وهو معطّل افتراضيًا لسبب واحد: أن مرمّزه أبطأ بنحو عشر مرات من مرمّز WebP، وهذه مقايضة خاطئة لأداة قد تشغّلها في كل مرة تحفظ فيها ملفًا. فعّله عند بناء الإصدار النهائي، واتركه معطّلًا أثناء العمل.

قيمة ‎`-q` رقم على مقياس JPEG/WebP، أما AVIF فلا يستخدم المقياس نفسه: فتمرير ‎`-q 82` إليه كما هو ينتج ملفًا *أكبر* من ملف WebP. ويحوّلها CPWO إلى مقياس AVIF نيابةً عنك، فتكفي قيمة ‎`-q` واحدة للصيغ الثلاث وتعني في كل منها الشيء نفسه تقريبًا.

في صور الكاميرا بأبعادها الكاملة تحتاج كل عملية ترميز AVIF إلى ذاكرة تزيد كثيرًا على غيغابايت. وقد بلغ استهلاك الذاكرة ذروته عند نحو 5 غيغابايت مع أربع صور بدقة 12 ميغابكسل وقيمة ‎`-j` الافتراضية، فاخفض ‎`-j` على جهاز بذاكرة RAM محدودة.

### تغيير حجم الصور

```sh
cpwo -r ./site                    # 1024, 512 and 256 wide
cpwo -sizes 512,256,128 ./site    # your own widths, -r implied
```

تُحفظ نسبة العرض إلى الارتفاع، ولا تُكبَّر أي صورة قط، فالمصدر الذي عرضه 400 بكسل يتخطى 512 و1024. ويبقى الملف الأصلي كما هو.

يشمل تغيير الحجم كل صيغة مفعّلة، فيعطي ‎`-r` وحده نسخ WebP، ويعطي ‎`-r -avif` الصيغتين معًا:

```
cpwo -r ./site           photo.jpg  ->  photo-512.webp  photo-256.webp
cpwo -r -avif ./site     photo.jpg  ->  photo-512.webp  photo-256.webp
                                        photo-512.avif  photo-256.avif
```

أضف ‎`-resize-fallback` إذا أردت نسخًا بالصيغة الأصلية نفسها لاستخدامها في ‎`<img srcset>`‎:

```
photo.jpg  ->  photo-512.webp  photo-512.min.jpg
               photo-256.webp  photo-256.min.jpg
```

الجزء ‎`.min.`‎ في اسم الملف الاحتياطي مهم، فهو يُبقي النسخة خارج الفحص التالي، وبذلك لا يستطيع تشغيل ثانٍ أن يحوّل `photo-512.jpg` إلى `photo-512-256.jpg`.

## بيانات EXIF

تُخزَّن الصورة الملتقطة بالوضع الرأسي عادةً بالوضع الأفقي، ومعها وسم اتجاه في EXIF يأمر برنامج العرض بتدويرها. ومفكّك ترميز الصور في Go يتجاهل هذا الوسم، ولا يعيد أي مرمّز كتابته، ولذلك يدوّر CPWO البكسلات بنفسه قبل أي خطوة أخرى. فيخرج كل ناتج، من ‎`.min.jpg` و‎`.webp` و‎`.avif` إلى كل نسخة بحجم مختلف، بالاتجاه نفسه الذي تظهر به الصورة الأصلية في متصفحك.

أما بقية كتلة EXIF فتُحذف افتراضيًا. فهي حمل زائد لا نفع منه في صورة الويب، وكثيرًا ما تبلغ عشرات الكيلوبايتات من إعدادات الكاميرا وصورة مصغّرة مضمّنة، وفيها تُخزَّن إحداثيات GPS.

أما ‎`-exif` فيُبقيها بدلًا من ذلك، من أجل الحالة الوحيدة التي يهمّ فيها الأمر، وهي ألا تفقد اسم المؤلف وحقوق النشر.

```sh
cpwo -exif ./site
```

يخضع هذا لقيدين، وكلاهما بنيوي لا اختياري:

- يقتصر أثره على ملف ‎`.min.jpg` المعاد ترميزه. ولا تستطيع صيغتا WebP وAVIF حمل هذه البيانات، لأن مرمّزيهما هنا لا يتيحان وسيلة لكتابتها، ولأن النسخة بحجم مختلف صورة غير التي تصفها البيانات، حتى في الأبعاد المسجّلة فيها.
- يُعاد ضبط وسم الاتجاه على القيمة 1 أثناء نسخه. فقد دوّر CPWO البكسلات بالفعل، ولو بقي الوسم يقول «دوِّرني» لدوّر برنامج العرض الصورة مرة ثانية.

وإذا بلغ المقطع من الكبر حدًّا يجعل ‎`.min.jpg` أكبر من المصدر، فتسري القاعدة المعتادة ويُبقي CPWO الأصل بدلًا منه.

## إعادة كتابة الوسوم

كلتا عمليتي إعادة الكتابة معطّلة افتراضيًا، لأنهما تغيّران وسوم HTML في مشروعك. ولا تمسّ أي منهما الملف المصدر؛ إذ لا تُعاد كتابة سوى النسخة المصغّرة.

يوجّه ‎`-relink` المراجع إلى نظائرها المصغّرة:

```html
<link rel="stylesheet" href="assets/css/style.css">     <!-- in  -->
<link rel=stylesheet href=assets/css/style.min.css>     <!-- out -->
```

أما ‎`-picture` فيغلّف الصور ويُبقي كل سمة كانت في ‎`<img>`‎:

```html
<img class="brand__tile" src="logo-128.png" alt="" width="46" height="46">
```
```html
<picture><source srcset="logo-128.avif" type="image/avif">
<source srcset="logo-128.webp" type="image/webp">
<img class="brand__tile" src="logo-128.png" alt="" width="46" height="46"></picture>
```

الترتيب مهم: يأخذ المتصفح أول ‎`<source>`‎ يفهمه، لذا يجب أن تأتي الصيغة الأصغر أولًا.

لا تعمل أي من العمليتين إلا إذا كان الملف البديل موجودًا فعلًا على القرص، وإن كان CPWO هو من أنتجه فيجب ألا يكون أقدم من الملف الذي أُنتج منه. وبذلك لا يستطيع CPWO أن يوجّه صفحة إلى ملف قرّر ألا يكتبه، ولا إلى نسخة قديمة. أما ملف ‎`.min.`‎ الذي تأتي به مكتبة خارجية فيكفي أن يكون موجودًا: فالأرشيفات تُفكّ بأي ترتيب، فلا يدل تاريخه على أنه مطابق لمصدره. ويترك CPWO على حالها عناوين URL الخارجية، ومراجع `data:`‎، والمراجع المنسوبة إلى جذر الموقع ‎`/…`‎، وكل ما يحمل ‎`.min.`‎ في اسمه أصلًا، وكل ‎`<img>`‎ داخل ‎`<picture>`‎ أصلًا، ووسوم ‎`<link>`‎ التي لا تخص CSS، مثل `rel="icon"`‎.

كذلك لا يمسّ ‎`-picture` أي ‎`<img>`‎ له `srcset`: فعنصر ‎`<source>`‎ واحد بالحجم الكامل سيتغلّب عليه في كل شاشة، فينزّل الهاتف الصورة الكبيرة. والأمر نفسه ينطبق على ‎`<img>`‎ فيه سمة `data-`‎ تحمل مسار صورة، لأن أداة التحميل الكسول تنقل ذلك المسار إلى `src` لاحقًا، وسيحجبه عندئذ أي ‎`<source>`‎ موضوع أمامه حجبًا نهائيًا.

لا يقدّم ‎`-picture` صيغةً إلا إذا تفوّقت على كل ما كان المتصفح سيحصل عليه بدونها. وهذه هي القاعدة التي يعمل بها CPWO في كل ما يكتبه (انظر [حواجز الحماية](#حواجز-الحماية))، ولذلك يجب أن يكون ‎`.avif` أصغر من ‎`.webp` ومن الصورة معًا.

تُعالَج الصور قبل HTML، فيجد الفحص الملفات الناتجة جاهزة. وتُعاد معالجة ملفات HTML في كل تشغيل ما دام أحد الخيارين مفعّلًا، لأن النتيجة تتوقف على الملفات المجاورة الموجودة، لا على الطابع الزمني للصفحة نفسها.

### إعادة التشغيل

يُتخطّى الملف الناتج إذا كان موجودًا وليس أقدم من مصدره، فالتشغيل الثاني لا يفعل شيئًا ولا يكلّف شيئًا. عدّل ملفًا واحدًا وسيُعاد إنتاجه وحده. ويعيد ‎`-overwrite` إنتاج كل شيء، لكن من ملفات CPWO نفسه فقط، ولا يكتب فوق ملف لم ينتجه CPWO أبدًا.

تخضع الملفات الناتجة عن تشغيلات سابقة للقاعدة نفسها التي تخضع لها الجديدة (انظر [حواجز الحماية](#حواجز-الحماية)). وحين لا يعود أحدها يستحق مكانه يحذفه CPWO: ملف ‎`.avif` يتفوّق عليه الآن ملف ‎`.webp` أصغر منه، أو ‎`.webp` أو ‎`.min.png` لصورة استُبدلت ولم يعد يتفوّق، أو نسخة بحجم آخر بقيت من وقت كان فيه المصدر أعرض. ولا يُحذف إلا ما يسرده ‎`.cpwo-output`. ويذكر ‎`-v` اسم كل ملف محذوف، ويحصي الملخص عددها (`N outdated removed`).

قد يؤدي تغيير ‎`-q` مع التشغيل بالخيار ‎`-overwrite` إلى حذف ملف ‎`.min.jpg` لم يعد يتفوّق على مصدره، فلا تربط ملفات ‎`.min.jpg` في صفحاتك يدويًا إن غيّرت ‎`-q`.

السجلات التي كتبها CPWO 0.2.1-beta أو إصدار أقدم منه كانت تُدرج كل ملف تجده محدّثًا في مسار ناتج، بما في ذلك ملف ‎`.webp` صُنع يدويًا. ومنذ 0.3.0 ما زالت بنودها تُعدّ من ملفات CPWO فيما يتعلق بالكتابة فوقها، كما كان الحال، لكنها لا تُحذف أبدًا: فالبند الذي كان سيُحذف لأنه متقادم يُستبعد من السجل ويُترك على حاله. وإلى أن يكتب CPWO بنفسه ملفًا كهذا، يذكره ‎`.cpwo-output` في سطر من الترويسة هو ‎`# Kept as found, never deleted: <path>`‎، فتبقى القاعدة سارية في كل تشغيل لاحق. والملفات المتبنّاة بالخيار ‎`-adopt` تحصل على السطر نفسه.

يُتخطّى كل ما يحمل ‎`.min.`‎ في اسمه، وكل ما ينتهي اسمه بامتداد ‎`.webp` أو ‎`.avif`. وهذا يشمل ما ينتجه CPWO نفسه، فلا يظهر لديك `style.min.min.css` أبدًا، ويشمل ملفات المكتبات الخارجية المضمّنة في المشروع: يبقى `bootstrap.min.css` و`bootstrap.bundle.min.js` كما صدرا تمامًا. ولا يدخل CPWO إلى `node_modules` ولا إلى `vendor` ولا إلى المجلدات التي تبدأ أسماؤها بنقطة.

## ملف ‎.cpwo-output

ملف واحد لكل مشروع. يسجّل ما وضعه CPWO في مشروعك، ولا شيء غيره.

```
# Written by CPWO v1.0.0 on 2026-08-21 16:55:57
# Result: 16 sources -> 21 generated files, 322.1 KB -> 259.0 KB (19.6% smaller)

# File Map

┌────────────────────────────┬────────────────────────────────┐
│ Source                     │ Generated                      │
├────────────────────────────┼────────────────────────────────┤
│ assets/css/style.css       │ assets/css/style.min.css       │
│ assets/img/logo-128.png    │ assets/img/logo-128.min.png    │
│                            │ assets/img/logo-128.webp       │
│ assets/js/app.js           │ assets/js/app.min.js           │
│ index.html                 │ index.min.html                 │
└────────────────────────────┴────────────────────────────────┘

# File Tree

.
├── assets
│   ├── css
│   │   └── style.min.css
│   ├── img
│   │   ├── logo-128.min.png
│   │   └── logo-128.webp
│   └── js
│       └── app.min.js
└── index.min.html
```

يصف السجل الملفات الموجودة، لا ما كتبه آخر تشغيل فحسب، ولذلك فإعادة التشغيل التي لا تغيّر شيئًا تعطيك مع ذلك القائمة الكاملة. والمسارات نسبية وتستخدم الشرطة المائلة الأمامية، والملف نص UTF-8 عادي بلا BOM، فيُقرأ على النحو نفسه في كل مكان.

يدمج كل تشغيل ما أنجزه في الملف القائم، لذا يُبقي التشغيل الأضيق نطاقًا (`cpwo -webp`) أو التشغيل على ملف واحد سجلَّ كل ما عداه. ويسجّل التشغيل على ملف (وهو ما يمرّره خطّاف الحفظ) أو على مجلد في أقرب ‎`.cpwo-output` عنده أو فوقه، ويتوقف البحث عند جذر مستودع Git. ولا يبدأ سجلًّا جديدًا هناك إلا حين لا يوجد أي سجل (وفي حالة الملف يبدؤه في مجلد الملف).

أما ملف ‎`.cpwo-output` الذي تركه تشغيل أقدم على مجلد فرعي واحد فيُدمج في سجل المشروع ثم يُحذف. وحين لا يبقى شيء من ملفات CPWO يُحذف ‎`.cpwo-output` نفسه.

### الملفات التي يتركها CPWO وشأنها

يقرأ CPWO ملف ‎`.cpwo-output` في بداية كل تشغيل، ولا يستبدل أو يحذف إلا ملفًا مدرجًا فيه، أو في ‎`.cpwo-output` أعلى منه في الشجرة. وأي شيء آخر موجود في موضع كان سيُكتب فيه ناتج يُترك وشأنه: كملف `bootstrap.min.css` الذي تأتي به مكتبة خارجية بجوار `bootstrap.css`، أو ملف ‎`.webp` صدّره أحدهم يدويًا.

قد يطلب مصدران الناتج نفسه، كما يطلب `photo.jpg` و`photo.png` معًا الملف `photo.webp`. وينال الناتجَ أولهما بحسب ترتيب الأسماء، في كل تشغيل، ويُترك الآخر وشأنه.

يحصي سطر الملخص هذه الحالات (`N left alone`)، ويسمّي ‎`-v` كل ملف منها ويذكر السبب. وإذا وُجدت ملفات ناتجة ولم يوجد ‎`.cpwo-output` يسردها (لأنه حُذف أو لم يُودَع قط)، يتركها CPWO وشأنها ويطبع تلميحًا يذكر عددها ويشير إلى ‎`-adopt`. وتشغيل واحد بالخيار ‎`-adopt` يتبنّاها، ويسردها السجل بعد ذلك.

### مع Git

أبقِ ‎`.cpwo-output` والملفات الناتجة معًا، فإما أن يُودَع الاثنان وإما أن يُتجاهلا. فبعد الاستنساخ يترك التشغيل التالي الملفات الناتجة المودَعة التي لا سجل معها وشأنها، ويطبع تلميحًا يشير إلى ‎`-adopt`. وتشغيل واحد بالخيار ‎`-adopt` يتبنّاها.

وإذا تجاهلتها فاستثنِ من التجاهل الملفات التي تصل مصغّرة أصلًا، لأن ‎`*.min.*`‎ يطابقها هي أيضًا. وافعل الشيء نفسه مع أي ملف ‎`.webp` أو ‎`.avif` صنعته بنفسك:

```gitignore
.cpwo-output
*.min.*
*.webp
*.avif
!bootstrap.min.css
!bootstrap.bundle.min.js
```

## حواجز الحماية

إذا جعل التحسين الملف أكبر، أبقى CPWO على الأصل. وهذا يحدث أكثر مما تتوقع: فعند ‎`-q 82` كثيرًا ما يكون WebP المضغوط مع فقد لشعار بألوان مسطحة أكبر من ملف PNG الأصلي. ولذلك تُرمَّز مصادر PNG مرتين، مع فقد وبلا فقد، ويُعتمد الأصغر منهما، فإن لم يتفوّق على المصدر مع ذلك فلا يُكتب ‎`.webp` أصلًا.

وتمضي القاعدة نفسها خطوة أبعد مع AVIF. يقدّم ‎`<picture>`‎ ملف ‎`.avif` أولًا، ولذلك لا يستحق ‎`.avif` مكانه إلا إذا تفوّق على ‎`.webp` وعلى المصدر معًا. من مجموعة شعارات حقيقية:

```
logo-512.png  23,799  ->  logo-512.webp   9,996  ->  logo-512.avif  5,881
logo-256.png  10,782  ->  logo-256.webp   8,586  ->  logo-256.avif  2,912
logo-32.png    2,667  ->  logo-32.webp      656  ->  no .avif, AVIF came out 756
```

وعندما ترفض أداة التصغير صياغة ملف ما، ينسخ CPWO الملف بدلًا من أن يخسره.

يُكتب كل ملف أولًا في ملف مؤقت ثم يُغيَّر اسمه إلى اسم الملف الهدف، فلا يترك التشغيل الذي ينقطع نصف ملف تعدّه التشغيلات اللاحقة محدّثًا.

لا تحصل الصورة التي يزيد عرضها أو ارتفاعها على 16383 بكسل على ملف ‎`.webp`، لأن هذا هو حدّ الصيغة. ويطبع CPWO تحذيرًا ويواصل عمله.

تُدوَّر الصور إلى وضعها الصحيح قبل إعادة ترميزها، فلا يمكن أن يقدّم ‎`<picture>`‎ ملف WebP مائلًا على جنبه إلى جانب JPEG بوضعه الصحيح. انظر [بيانات EXIF](#بيانات-exif).

يحتفظ CPWO بقيم السمات الافتراضية في HTML. فحذف `type="text"`‎ من ‎`<input>`‎ صحيح في HTML ويوفّر بضعة بايتات، لكنه يمنع أيضًا كل قاعدة CSS مثل `input[type="text"]`‎ وكل `querySelector` من مطابقة العنصر. وتبقى الصفحة تُعرض، لكنها تبدو خاطئة. ولن يقبل CPWO بهذه المقايضة.

## ما يحدث لكل ملف

| الامتداد | الإجراء |
|---|---|
| `.html .htm` | يُصغَّر، ويُضاف ‎`-relink` و‎`-picture` إن طُلبا |
| `.css .js .mjs .json .svg .xml` | يُصغَّر |
| `.jpg .jpeg .png` | يُعاد ضغطه بالجودة ‎`-q`، ويُكتب بجواره ملف ‎`.webp`، ومعه ملف ‎`.avif` عند استخدام ‎`-avif` |
| `*.min.*`, `*.webp`, `*.avif` | يُتخطّى، لأنه مصغّر أصلًا أو من إنتاج CPWO نفسه |
| أي شيء آخر | يُترك على حاله |

تبقى الملفات الأصلية في مكانها، فتظل البدائل الاحتياطية في ‎`<picture>`‎ تعمل، وهذا ما يكتبه لك ‎`-picture`.

## تحديث التبعيات

يسرد السكربت `scripts/deps.sh` كل وحدة Go مع إصدارها الحالي وأحدث إصدار لها ومستودعها، ثم مكتبات C المترجمة داخل المرمّزات وسلسلة أدوات Go وإجراءات GitHub Actions المستخدمة، ويبيّن أيها له تحديث.

```sh
scripts/deps.sh             # what has an update
scripts/deps.sh --apply     # update the outdated modules, go mod tidy, run the tests
scripts/deps.sh licenses    # regenerate licenses.md
```

يعيد `licenses` كتابة [licenses.md](licenses.md). شغّله بعد أي تحديث للتبعيات، لأن اختبارًا سيفشل إلى أن تفعل. ويحتاج السكربت إلى bash وcurl، وإلى Go أيضًا من أجل ‎`--apply` و`licenses`. ويرفع `GITHUB_TOKEN` حدّ GitHub البالغ 60 استدعاءً لواجهة API دون مصادقة في الساعة.

## البناء

```sh
go mod tidy
go test -tags nodynamic ./...
go build ./...
```

يجب أن ينجح الأمر `go test -tags nodynamic ./...`‎. فبدون هذا الوسم تستخدم المرمّزات libwebp/libavif الموجودة في النظام إن كانت مثبّتة، فتقيس الاختبارات مرمّزًا يختلف عن المرمّز الذي يُشحن. ثم يترجم `scripts/build.sh` الأهداف الستة كلها ترجمةً متقاطعة إلى `bin/<os>-<arch>/`‎، مثل `bin/linux-amd64/cpwo` و`bin/windows-amd64/cpwo.exe`. ويكتب أيضًا `bin/SHA256SUMS`، ويتحقق، إذا كان `file` مثبّتًا، من أن ملفات Linux التنفيذية ساكنة الربط (static).

```sh
scripts/build.sh                             # all six targets
scripts/build.sh linux/amd64 windows/amd64   # only these
VERSION=1.2.3 scripts/build.sh               # stamp a version
```

يؤخذ رقم الإصدار افتراضيًا من وسم Git، ومن الإصدار المكتوب في `main.go` إذا لم يوجد وسم.

تُبنى نسخ الإصدار باستخدام ‎`-tags nodynamic`. فبدونه تبحث حزمتا WebP وAVIF عن libwebp/libavif في النظام عند بدء التشغيل، فلا يعود ملف Linux التنفيذي ساكن الربط. ولبناء محلي سريع:

```sh
CGO_ENABLED=0 go build -tags nodynamic .
```

على GitHub يشغّل كل push وكل pull request الاختبارات على Linux وWindows وmacOS، ثم يبني الأهداف الستة كلها. وتُرفق الملفات التنفيذية بتشغيل سير العمل في صورة artifact باسم `cpwo-<commit>`‎. وعند دفع وسم `vX.Y.Z` تُشغَّل الاختبارات ويُنشأ إصدار باستخدام GoReleaser، الذي يبني الأهداف الستة نفسها.
